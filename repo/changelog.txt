v0.2.85
- THE reason every DarkSubs source patch "didn't apply": DarkSubs
  (service.subtitles.All_Subs) declares reuselanguageinvoker=true and
  runs autosub.py as a persistent xbmc.service. Its Python interpreter
  loads autosub.py/engine.py/sub_window.py into memory at boot and stays
  alive all session, so rewriting those files on disk + dropping the .pyc
  never takes effect this session (and a restart races and loses). That's
  why the embedded-subtitle demote/insert (and other DarkSubs patches)
  appeared to do nothing.
  * New darksubs_reload: after any DarkSubs source patch actually changes
    a file, disable+enable the DarkSubs addon via JSON-RPC so its
    interpreter is torn down and re-imports the PATCHED source. Debounced
    to once per startup; only cycles when something changed (no churn on
    steady-state boots). Wired so the embedded-insert / embedded-demote /
    subwindow-demote patches trigger it. This is what makes the
    embedded-English-at-the-bottom fix finally take effect.

- What it does: when DarkSubs hands an English SRT to translate,
  resolve() now emits a `first_ready` callback the moment the
  source is in memory (~3 seconds in). default.py uses that to
  write the English fallback to DarkSubs's output path and touch
  the `.ai_done` sentinel so DarkSubs releases immediately --
  Kodi shows English subtitles in seconds instead of 1-3 minutes.
- The same RunScript subprocess keeps translating (existing
  parallel chunked Gemini flow). As each chunk lands, resolve()
  emits a `chunk_ready` callback with a Hebrew-where-done /
  English-where-pending merged SRT; default.py writes that to a
  versioned `progressive_<id>_vN.he.srt` file in cache_dir and
  calls `xbmc.Player().setSubtitles(new_path)` to swap subtitles

  cache) so the NEXT pick of that same source shows `[CACHE]`
  and resolves instantly.
- Abort path: a partial Hebrew translation never lands in the
  canonical cache. The .vN files are left on disk for the
  existing TTL prune to clean up.
- Also wired into the native subtitle picker -- click an AI

- English-source only. The fast path briefly shows the SOURCE SRT

v0.2.46
- Fix Hebrew toast notifications reading left-to-right (visually
  reversed for Hebrew readers). User report: "ההודעה של התוסף
  שקופץ במסך בזמן תרגום, הפוך. הוא מקריא מהסוף להתחלה (משמאל
  לימין)."
- Previous attempt used U+200F (RIGHT-TO-LEFT MARK) as a prefix.
  RLM is just a strong-RTL invisible character that BIASES the
  BiDi algorithm's first-strong heuristic but doesn't OVERRIDE
  the paragraph direction. When messages like "AI: 25% תורגם
  (5/20 chunks)" have more LTR character weight than RTL, RLM
  loses to first-strong from "AI:" and Kodi renders the toast
  left-to-right -- which to a Hebrew reader looks reversed.
- Switched to U+202B (RIGHT-TO-LEFT EMBEDDING) + U+202C (POP
  DIRECTIONAL FORMATTING) wrap. RLE/PDF is the proper Unicode
  mechanism to FORCE a paragraph's base direction to RTL while
  still letting embedded Latin/digit runs ("AI: 25%", "(5/20
  chunks)") read left-to-right within the RTL paragraph. The
  whole toast now scrolls and aligns from the right as a Hebrew
  reader expects, with Latin segments rendered in their natural
  LTR order inside the RTL frame.
- notify() also strips any existing BiDi-marker prefix from old
  messages before wrapping, so we don't end up double-wrapped
  if a caller (or a future re-call) re-passes an already-RTL'd
  string.

v0.2.44
- v0.2.43 finally rendered the modal correctly (white_pixel.png as
  the colorDiffuse base fixed the all-black box). User screenshot
  confirmed: the card LOOKS right -- yellow title, navy panel,
  branded subtitle, status text. But the percent number stayed at
  "0%" and the status at "מתחיל תרגום..." for 3 minutes while
  translation actually progressed in the background. The labels
  were never updating.

- Root cause: xbmcgui control updates (setLabel, setPercent) called
  from a non-UI thread don't reliably land on screen. The doModal()
  architecture in v0.2.42 moved translate.resolve into a daemon
  worker thread; that thread's calls to window.update_progress()
  hit the controls but Kodi's UI thread, busy rendering doModal,
  apparently didn't pick the changes up.

- Fix: switch to Kodi's canonical cross-thread UI pattern --
  Window(10000) properties + $INFO[] binding in the label text.
  setProperty is documented thread-safe; the UI thread re-reads
  $INFO[Window(10000).Property(...)] on every render tick so
  updates land within ~50 ms regardless of which thread wrote them.

  Properties used:
    ai_subs.progress_pct        -- current %
    ai_subs.progress_chunks     -- "chunk X / Y" or status text
    ai_subs.progress_heartbeat  -- "מתרגם... Ns" elapsed-seconds ticker

  Labels in the modal now contain literal $INFO[...] markers that
  Kodi auto-expands; update_progress() and update_heartbeat()
  just call setProperty.

- NEW heartbeat ticker thread updates `progress_heartbeat` every
  second with the elapsed-seconds count + an animated dots glyph
  ("מתרגם... 12ש"). Critical for the Gemini-overload-retry case:
  the first chunk can take up to 230 s before completing if Google
  is rate-limiting (5 backoff steps of up to 120 s each). With the
  heartbeat, the user sees the elapsed counter advancing the whole
  time -- the modal feels alive, not frozen.

- Dropped the visible ControlProgress bar in this revision. It
  can't bind to a Window property the way ControlLabel can, so it
  would still need cross-thread setPercent() calls. The big
  percent number + chunk text + heartbeat counter convey the same
  information and DO auto-update correctly.

v0.2.38
- Four targeted improvements to Hebrew gender (זכר/נקבה) accuracy
  in AI translation. Today the gender form is right ~90% of the
  time; the remaining 10% mostly traces to four specific failure
  modes that these changes address. No behavioural change for any
  non-Hebrew code path.

- (a) Cross-chunk context carry-over: we translate in parallel
  chunks (default 250 entries each). Until now, each chunk was
  translated INDEPENDENTLY: the AI saw the cast block but no
  recent conversational thread, so a character finishing a line
  at the end of chunk N would sometimes get a different gender
  the moment they spoke at the start of chunk N+1. We now feed
  the last 5 SOURCE-text lines of chunk N-1 into chunk N's
  prompt as a "PREVIOUS DIALOGUE CONTEXT" section -- AI sees the
  thread, picks up the gender consistently. The previous chunk's
  source is precomputed up-front (deterministic per index) so
  parallel dispatch still works -- no inter-chunk dependency.
  Tunable via the `prev_context_lines` setting (default 5;
  0 disables the feature).

- (b) Speaker-prefix hints: SRT entries that start with an
  ALL-CAPS speaker tag like "MABEL:" or "DR. SMITH:" used to be
  dropped on instruction ("do NOT include speaker prefixes in
  the Hebrew"). The prompt now tells the AI to MATCH the prefix
  name against the cast block, use that person's gender for
  first-person forms in the line, then drop only the prefix
  from the output. Speaker prefixes are common in SDH /
  Telegram SRTs and were previously thrown away even though
  they're the strongest gender signal we ever get.

- (c) Reply heuristic: in two-character dialogues, short
  follow-up lines ("Right.", "No way.", "You sure?", "I told
  you.") are almost always REPLIES from the OTHER speaker.
  New explicit prompt rule: "speakers alternate unless context
  says otherwise; apply alternation before falling back to a
  gender guess." Catches the most common single-line gender
  flip in dialogue.

- (d) Cast list widened from top-12 to top-25 (`tmdb_helper`
  default). Minor characters (waiters, partners, one-scene
  parents) whose gender mattered for the line they spoke were
  often outside the top-12 cut and defaulted to the AI's
  best guess. Existing cached cast lookups with fewer than
  20 entries are treated as cache misses and re-fetched on
  next translation, so users with prior watches get the
  expanded list automatically without manual cache clear.

v0.2.36
- Fix (a): iOS Smart Punctuation replaces ASCII hyphen-minus
  (U+002D) with em-dash (U+2014) for `--` and en-dash (U+2013) for
  a lone `-`. NFKC does NOT collapse these back to ASCII -- they're
  distinct Unicode codepoints. v0.2.34's allow-list regex stripped
  them entirely, so an iPhone-pasted `AIza...XYZ-ABC` arrived at
  our server as `AIza...XYZABC`, two characters short, and Google
  rejected the truncated string with 400.

  back to ASCII `-` BEFORE the allow-list runs. Covers 11 variants:
  em-dash, en-dash, minus sign, unicode hyphen, non-breaking
  hyphen, figure dash, horizontal bar, hyphen bullet, full-width
  hyphen-minus, and the small-form variants. Verified against an
  end-to-end PairServer POST with em-dash corruption.

     write. Wipes engine.cpython-*.pyc so Python is forced to
     re-compile from the new .py the next time DarkSubs imports it.

     means the patch lives on disk but never reaches RAM.

  2. Hook v2 (HOOK_VERSION = 2) is loud. Every fire writes:
       * Window(10000).Property('ai_subs.hook_last_fire')  = timestamp
       * Window(10000).Property('ai_subs.hook_last_key_len') = key len
       * Window(10000).Property('ai_subs.hook_last_outcome') =

     (timeout / no key / crash) -- so the user SEES why instead of

     to v2; v1 → v2 migration handled by the existing OLD_MARKERS

v0.2.5
- RTL punctuation fix now handles HTML-wrapped lines. Gemini
  often emits italicised speech as "<i>.לעזאזל</i>" -- the
  previous regex couldn't see past the opening tag and left the
  period at the start. The screenshot the user kept hitting was

  marker). Existing tests + 16-case unit suite all green.

  updated regex to already-saved files that were affected.

v0.2.4
- Toast notifications now scroll right-to-left as Hebrew should.
  Kodi's notification widget infers paragraph direction from the
  first strong character in the message body. Most of our
  notifications start with "AI: ..." (Latin 'A' = strong LTR),
  so the widget set paragraph direction to LTR and scrolled
  left-to-right when the text overflowed. Prepending an invisible
  RIGHT-TO-LEFT MARK (U+200F) in kodi_utils.notify() flips the
  inference to RTL. Single point of fix; applies to every notify
  call site in the addon automatically.
